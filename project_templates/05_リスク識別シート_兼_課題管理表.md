# 05. リスク識別シート（CSA）兼 課題管理表（Ⅲ-4.10 ／ Ⅳ-3.1〜3.2 ／ Ⅳ-4.1〜4.3）

> **リスクと課題の管理ルール（Ⅳ-3 ／ Ⅳ-4）**
> 1. **リスク**：まだ発生していない「不確実性」。4つの監視タイミング（①部門推進会議、②フェーズ移行時、③イテレーション開始/終了時、④月次報告時）で再評価する。
> 2. **課題**：既に顕在化し、解決しないとその先へ進めない「問題」。**リスクが顕在化したら直ちに下部の「課題管理表」へ移動**させる。
> 3. **行削除禁止（履歴保持の鉄則）**：解消したリスクや完了した課題も**絶対に行削除せず**、ステータスを「完了（クローズ）」とし取消線（`~~テキスト~~`）や網掛けで全履歴を残す。

## 2. 領域別リスク洗い出しチェックリスト（6領域）（Ⅲ-4.10 (4)〜(9)）

プロジェクト計画時およびフェーズ移行時に、以下の典型リスクが潜んでいないか点検する。

- [ ] **(1) ユーザコントロール**：会議での非協力的態度、要求・テスト能力不足、非現実的な期待、意思決定の遅れ、ユーザPMの経験不足、情シスと利用部門の連携不足、作成物の品質疑問、利用者層の特定問題
- [ ] **(2) 成果物調達管理（協力会社・当社）**：
  - 協力会社側：責任者不在、標準未遵守、曖昧・虚偽報告、要員不足、セキュリティ意識欠如
  - 当社側：検査計画の曖昧さ、標準・品質基準未提示、スケジュール余裕なし、**協力会社作業者への直接指示（偽装請負）**、丸投げ・名ばかりPM、納入成果物未記載、下請法抵触の値引き強要
- [ ] **(3) 大規模プロジェクト**：派遣要員のスペース・端末・インフラ費用増大、専任庶務・PMO担当の不足
- [ ] **(4) 要件定義**：要件をまとめられない、承認者・範囲が未定、曖昧な記述、外部IF資料の不明確・不在、ステークホルダ役割未定、終了ゴール不明確、非機能要件（性能・信頼性・セキュリティ・SLA/SLO）の制約不明確
- [ ] **(5) 設計時**：真の決定権者による未確認、移行設計不明確（旧設計書不信）、非機能要件の設計漏れ、別ベンダのインフラ設計遅れ、未知技術の採用・性能未検証、設計標準への不慣れ、例外処理の未検討
- [ ] **(6) テスト時**：複数テスト環境の必要性、不明確だった非機能要件へのクレーム、本番と異なるOS・ミドルウェアバージョンの使用、画面操作性の不統一、パフォーマンス未達、顧客からのテストデータ未提供
